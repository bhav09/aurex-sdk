The pattern across all six competitors
There is a clear split by positioning. Tools targeting enterprise buyers and evaluation workflows (Braintrust, LangSmith) go light-dominant — it reads as trustworthy, legible, and professional. Tools targeting AI Engineers and AIOps who live in terminals and dark IDEs (Arize, Raindrop, Maxim) go dark-first — it reads as native to their environment. Langfuse, the most popular open-source option, supports both equally well. Every single platform uses an accent colour that is either blue/indigo/purple or teal/cyan — the cool end of the spectrum. None use warm primaries (orange, red, yellow) for their brand accent. This is not coincidence — it is colour psychology at work for a technical audience.
Colour psychology — what AI Engineers, AIOps, and Startups actually respond to
AI Engineers — environment match
This persona spends 8+ hours daily in VS Code, terminal, Jupyter notebooks — all dark mode environments. A dark-mode tool feels native; a light-mode tool creates visual context-switching friction. They trust tools that look like their environment, and distrust tools that look like marketing.
AIOps — precision and control signals
AIOps buyers think in incident response, runbooks, and SLAs. They respond to colours that signal status — green for healthy, amber for warning, red for critical. Their mental model comes from Datadog, Grafana, PagerDuty — all dark-mode dashboards. Light mode reads as a CRM, not an ops tool.
Startups — credibility and speed
Startup CTOs and founders need to trust a tool before installing it in production. Dark + clean = "serious tool." They've been burned by bright, cheerful SaaS tools that looked friendly but lacked depth. A polished dark UI signals engineering-first culture, which is exactly the signal Aurex needs to send.
Why cool accents (teal, blue) over warm (orange, red)
Cool colours — teal, blue, cyan, indigo — psychologically encode precision, reliability, and intelligence. Warm colours encode urgency and risk. You want Aurex to feel like precision instrumentation, not a warning siren. The exception: use amber/red sparingly for actual warning states (loop detected, budget exceeded) so they carry real semantic weight.
Aurex colour system recommendation — the verdict
Recommendation: dark-first, light-available — with a teal primary accent
Keep the dark mode as the default and primary experience. Do not switch to light-first. Your three user personas — AI Engineers, AIOps, and Startups — all skew strongly toward dark mode by environment and habit. However, build a proper light mode as a full toggle option (system preference + manual), because enterprise procurement reviewers, conference demos on bright stages, and team leads sharing screenshots in Notion all need light mode to work well. The current Aurex dark mode is a good foundation — the issue isn't the mode, it's the colour choices within it.

Why teal as the primary, not purple or blue
Langfuse uses indigo. Arize uses purple. Raindrop uses cyan. Maxim uses indigo-violet. Every competitor converges on the indigo/purple/blue cluster. Teal occupies adjacent territory (cool, precise, technical) but is visually distinct in a sea of purple AI tools. It also carries a specific psychological meaning — efficiency and clarity — that maps directly to Aurex's prevention-first positioning. On dark backgrounds, teal has excellent luminance contrast without feeling aggressive like cyan or cold like pure blue.

Documentation colour and typography rules
ElementSpecificationWhy
Code block themeGitHub Dark (#0d1117 base, #e6edf3 text) for dark mode. GitHub Light for light mode. Syntax colours: strings green (#a5d6ff), keywords purple (#ff7b72), functions yellow (#d2a8ff).GitHub's palette is familiar to every engineer. Using it reduces the cognitive load of reading unfamiliar code. Do not invent a custom syntax theme — familiarity wins over originality here.
Inline codeMonospace, 0.875em, background #21262d (dark) / #f6f8fa (light), padding 2px 6px, border-radius 4px, no border.Should feel like a inline terminal fragment, not a styled callout box.
Callout boxesFour types only: Note (blue left-border), Warning (amber left-border), Danger (red left-border), Tip (teal left-border). No icons needed — left-border colour is the signal.AI Engineers read docs for information density, not decoration. Icons in callout boxes add noise without signal. The border colour is sufficient.
Table stylingNo zebra striping. Thin 0.5px row borders only. Column headers in secondary text colour, not bold. Monospace for type/value columns.Heavy table styling (striped rows, dark headers) makes parameter tables feel like a spreadsheet rather than a reference document.
Heading hierarchyH1: page title only, 28px, weight 500. H2: major sections, 20px, weight 500, top border separator. H3: subsections, 16px, weight 500, no border. Never use H4+ — restructure instead.Deep heading hierarchies signal poorly organised content. If you need H4, split the page.
Font choiceInter for body (the one context where Inter is appropriate — it was designed for documentation readability). JetBrains Mono for all code. Both self-hosted, not CDN-loaded.Inter at 14px/1.7 line-height is optimised for dense technical content. JetBrains Mono has the best character disambiguation (0 vs O, 1 vs l) of any free coding font.
SearchCmd+K global search that searches across all docs content including API parameters and code examples. Results grouped by section.Engineers use keyboard search, not nav browsing. If your docs don't have Cmd+K search, engineers will use Google to search your own docs — and sometimes land on a competitor page instead.
